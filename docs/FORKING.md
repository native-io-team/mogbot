# Forking & shipping your own distribution

This guide is for developers who want to **fork Mogbot and publish their own
signed, auto-updating builds** under a different name, identity, or telemetry
configuration.

If you just want to **contribute back** upstream, read
[CONTRIBUTING.md](../CONTRIBUTING.md) instead.

---

## What's involved

A production release ships:

- A **macOS** `.dmg`, signed with a Developer ID and notarised by Apple. It is
  made by hand on a Mac with `scripts/release-mac.sh` (Apple Silicon by
  default, `--universal` for Apple Silicon + Intel). There is no release
  workflow in CI.
- **Windows** (`.exe`, `.msi`) and **Linux** (`.deb`, `.rpm`, `.AppImage`)
  installers, built by `.github/workflows/build-installers.yml` as workflow
  artifacts. Windows signing is optional (SmartScreen reputation builds over
  time without it).
- **Auto-updater artifacts** (`latest.json` + signed update bundles) so
  installed builds upgrade themselves.

Forking means owning each of those. The full process upstream follows is in
[RELEASING.md](../RELEASING.md); most of what you change is `brand.json`, a
few checked copies of it, and your own keys.

## 1 — Brand & identifiers

The app's name and identity live in one file, the repo-root `brand.json`:
`name`, `slug`, `identifier` (the bundle id), `urlScheme`, `appDirName`,
`repository`, `companion` (the phone app's scheme, bundle id and tailnet
port), every external link under `links` (null turns that feature off), and
`telemetry`. The frontend reads it through `src/lib/brand.ts`; the Rust side
gets constants generated by `src-tauri/build.rs`.

A few files can't import it and carry a copy. `pnpm check:brand` (also run in
CI) fails on any drift, and `node scripts/check-brand.mjs --write` rewrites
the generated ones:

| File | Field | What to change |
|------|-------|----------------|
| `src-tauri/tauri.conf.json` | `productName`, `identifier`, `plugins.deep-link.desktop.schemes` | Match `name`, `identifier` and `urlScheme` (checked) |
| `src-tauri/tauri.conf.json` | `plugins.updater` | Present exactly when `links.updates` is set; its one endpoint is `links.updates`, its `pubkey` *your* key (see §3) |
| `package.json` | `name`, `version`, `description`, `repository`, `homepage` | `name` = `slug`. `version` is the one version (`tauri.conf.json` reads it). **Must be semver** — the updater compares versions |
| `src-tauri/Cargo.toml` | `[package].name`, `version`, `description`, `authors`, `repository`, `homepage` | `name` = `slug`, `version` = `package.json`'s |
| `README.md`, `CONTRIBUTING.md`, etc. | Repo URLs | Your project |

`brand.json`'s `previous` describes the last rename (the app was Dashbot) and
moves that name's data on first launch; read "Brand and identity" in
[CLAUDE.md](../CLAUDE.md) before changing it.

> **Why the bundle identifier matters.** macOS treats two binaries with the
> same identifier as the same app. If you ship `io.native.mogbot`, macOS
> thinks your build is the upstream app. Change the identifier (and
> `companion.bundleId`, or the phone apps collide) before your first
> release.

## 2 — Code signing

### macOS (required for release)

Without code signing and notarisation, Gatekeeper blocks the app on other
Macs. You need:

1. **An Apple Developer account** ($99/year).
2. **A Developer ID Application certificate** in your login Keychain
   (Xcode → Settings → Accounts → Manage Certificates → `+` →
   **Developer ID Application**).
3. **A notarytool keychain profile**, made once:

   ```bash
   xcrun notarytool store-credentials <profile> --apple-id <your Apple ID> --team-id <TEAM_ID>
   ```

`scripts/release-mac.sh` signs with the identity in
`MOGBOT_SIGNING_IDENTITY` and notarises with the profile in
`MOGBOT_NOTARY_PROFILE`. Both default to the upstream owner's, so set them
for your fork. Without the profile the script still builds and signs, says
so, and skips notarisation. `--skip-notarize` is a dry run.

### Windows (optional but recommended)

Without code signing, Windows SmartScreen warns users on first launch.
`build-installers.yml` signs with Azure Trusted Signing when the repo has the
secrets `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` and the
variables `TRUSTED_SIGNING_ENDPOINT`, `TRUSTED_SIGNING_ACCOUNT`,
`TRUSTED_SIGNING_PROFILE`; without them the installers are unsigned. Other
certificates: the
[Tauri Windows signing guide](https://tauri.app/distribute/sign/windows/).

## 3 — Tauri updater keypair

The updater verifies downloaded bundles against a public key compiled into
the app. Generate your own keypair — never reuse the one in this repo.

```bash
pnpm tauri signer generate -w ~/.tauri/<slug>-updater.key
chmod 600 ~/.tauri/<slug>-updater.key
```

This produces:

- `~/.tauri/<slug>-updater.key`     — **private key, keep secret and back it
  up.** Losing it means no installed copy can ever update again.
- `~/.tauri/<slug>-updater.key.pub` — public key, for `tauri.conf.json`.

In `src-tauri/tauri.conf.json` (the endpoint must equal `links.updates`):

```json
"plugins": {
  "updater": {
    "pubkey": "<contents of <slug>-updater.key.pub, on one line>",
    "endpoints": [
      "https://github.com/<you>/<releases-repo>/releases/latest/download/latest.json"
    ],
    "requireSignedVersion": true
  }
}
```

`release-mac.sh` reads the key from `MOGBOT_UPDATER_KEY` (default
`~/.tauri/<slug>-updater.key`) and its password from the login-Keychain item
`<slug>-updater-key-password` (account `release`), or
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. For Windows and Linux update bundles,
add the same key to the repo's secrets:

| Secret | Source |
|--------|--------|
| `TAURI_SIGNING_PRIVATE_KEY` | contents of the private key |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | its password (or empty) |

No updates at all: set `links.updates` to null and remove `plugins.updater`
(`pnpm check:brand` requires both or neither).

## 4 — Release infrastructure

Upstream uses a **two-repo split**:

- **Source repo** — `native-io-team/mogbot` (this one). Where development
  and PRs happen.
- **Releases repo** — `native-io-team/mogbot-releases` (`links.releases`).
  Where the DMG, installers, update bundles and `latest.json` are published.
  The updater endpoint points here.

`./scripts/release-mac.sh --publish` creates the release on the repo
`links.releases` names, with `gh`. Windows and Linux installers are attached
by hand from a `build-installers.yml` run (the steps are at the top of that
workflow, using `scripts/latest-json-add-platforms.mjs`). Nothing in CI
publishes anything.

The split keeps the source repo's release tab uncluttered. **For a fork it's
optional**: point `links.releases`, `links.updates` and the updater endpoint
at your source repo's releases instead. Either way, `gh` must be signed in
with write access to the releases repo.

## 5 — Telemetry

Telemetry is **off unless `brand.json` names it**, and upstream ships it off:

- `telemetry.posthogKey` / `telemetry.posthogHost` — product analytics
  ([docs/analytics.md](analytics.md) lists every event).
- `telemetry.sentryDsn` — crash reports, desktop and frontend.
- `links.errorReports` plus the build-time `BUG_REPORT_SECRET` — automatic
  error reports; a build without the secret sends none.

They're compiled in, so null means nothing is sent. To turn one on, put your
own key there and rebuild. Verify after building that no requests go to
domains you didn't configure.

## 6 — Optional: support / identity integrations

The cStar.help support widget and its build-time `CSTAR_IDENTITY_SECRET` are
gone: nothing in the code reads it any more, and CI no longer passes it.
Community links (issues, discussions, community chat) come only from
`brand.json`'s `links`; null hides each one.

---

## 7 — CI: handling forked PRs

`.github/workflows/ci.yml` uses no repository secrets, so a fork's PR runs the
same jobs as the main repo. `dependency-security-scan.yml` uses only the
built-in `GITHUB_TOKEN` to post its PR comment, and that step is
`continue-on-error` because a fork's token is read-only. Mac signing and
notarisation are local scripts (`scripts/release-mac.sh`,
`mobile/scripts/store-ios.sh`), never CI.

## 8 — First release checklist

Once your fork is configured:

- [ ] `brand.json` names your app, identifier, schemes, companion bundle id
      and links; `pnpm check:brand` passes.
- [ ] `tauri.conf.json` → updater endpoint and pubkey are yours (or the
      updater is removed with `links.updates` null).
- [ ] Your Developer ID identity and notary profile are set
      (`MOGBOT_SIGNING_IDENTITY`, `MOGBOT_NOTARY_PROFILE`).
- [ ] GitHub Secrets, if you build Windows/Linux: `TAURI_SIGNING_*` (×2),
      and the Azure Trusted Signing secrets and variables if you sign.
- [ ] Tested a release end-to-end: `./scripts/release.sh`, then
      `./scripts/release-mac.sh`; the signed `.dmg` opens on a clean macOS
      install without Gatekeeper warnings.
- [ ] Tested auto-update: previous build → new build, "Restart to update"
      appears, restart succeeds.
- [ ] LICENSE preserved (MIT requires the copyright notice to stay).
- [ ] Release notes (`docs/release-notes-<version>.md`) describe your
      changes vs. upstream.

## Staying in sync with upstream

Forks that track upstream changes:

```bash
# add upstream remote (once)
git remote add upstream https://github.com/native-io-team/mogbot.git

# pull upstream changes
git fetch upstream
git merge upstream/main  # or rebase, depending on your preference
```

Watch the upstream [releases](https://github.com/native-io-team/mogbot-releases/releases)
for security-relevant fixes.

If you ship a meaningful improvement, **please send a PR back to upstream**
— the project is stronger when downstream forks share what they've built.
